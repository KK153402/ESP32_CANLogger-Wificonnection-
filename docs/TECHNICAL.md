## 1. そもそも何をする装置か

### 解決したい問題

CANログを取るには通常、PCとCANインタフェース（Vector社のVNシリーズなど）が要る。
だが現場では、PCを持ち込めない・機材の台数やライセンスが足りない・
測定対象のそばにPCを置けない、といった制約がある。

そこで**PCなしで単独動作し、SDカードへ記録するだけの装置**を作る。

### この治具がやること

```
測定対象のCANバス  →  治具がSDカードへ記録  →  PCでBLF形式に変換  →  CANalyzerで解析
```

治具は**通信内容をそのまま丸ごと記録するだけ**で、中身の意味は解釈しない。
意味の解釈（「このビットは何のフラグか」など）はCANalyzerとDBCファイルが行う。

だから治具はDBCを持たないし、信号が何本あろうと動作は変わらない。

### なぜ「BLF」に変換するのか

BLF（Binary Logging Format）はVector社のログ形式で、CANalyzerがそのまま読み込んで
**再生（リプレイ）**できる。既存の解析環境をそのまま使えるようにするための選択。

## 2. CANバスの基礎

### CANとは

自動車や産業機器で使われる通信規格。**2本の線（CAN-H / CAN-L）**の電圧差で
0と1を表現する（差動信号）。ノイズに強いのが特徴。

### フレーム（1回の通信の単位）

CANでは1回の通信を**フレーム**と呼ぶ。中身はこうなっている。

| 要素 | 内容 | この治具での扱い |
|---|---|---|
| **ID** | 送信内容の識別番号。11bitか29bit | `CanRec.id` に保存 |
| **DLC** | データの長さ（0〜8バイト） | `CanRec.dlc` に保存 |
| **データ** | 最大8バイトの中身 | `CanRec.data[8]` に保存 |
| RTR | リモートフレーム（データ要求）かどうか | `CanRec.flags` のbit1 |
| CRC | 誤り検出符号 | コントローラが検証。記録しない |
| ACK | 受信確認 | **この治具は返さない**（後述） |

**IDには宛先の概念がない。** 全ノードが全フレームを受信し、IDを見て
「自分に関係あるか」を判断する。だから治具のような傍受装置が成立する。

### ビットレート

1秒間に何ビット送れるか。この治具では2種類を扱う。

| チャネル | ビットレート | 1フレームの所要時間（8バイト時） |
|---|---|---|
| CH1 | 500 kbps | 約 222〜260 µs |
| CH2 | 250 kbps | 約 444〜520 µs |

**ビットレートが合っていないと、1フレームも読めない。** 波形の切り出し位置がずれるため、
全部が「壊れたフレーム」として捨てられる。開発中、CH2（250k）に500k設定で繋いで
0件になった事例がこれ。

### Listen-Only（傍受専用）モード

通常のCANノードは、フレームを正しく受信すると**ACKビットを返す**（電気的にバスを引っ張る）。
つまり「聞くだけ」のつもりでも、実はバスに手を出している。

**Listen-OnlyモードではこのACKも返さない。** バスに対して完全に受動的になる。

| | 通常モード | Listen-Only |
|---|---|---|
| 受信 | できる | できる |
| ACK送信 | **する** | **しない** |
| バスへの影響 | あり | **なし** |
| ビットレート誤設定時 | エラーフレームを出して**バスを妨害する** | 静かに0件で終わる |

稼働中の機器に繋ぐ治具なので、**バスに一切影響を与えない**ことが絶対条件。
CH1（ESP32内蔵TWAI）は `TWAI_MODE_LISTEN_ONLY`、CH2（MCP2515）は
`CANCTRL` レジスタに `0x60` を書いてListen-Onlyにしている。

その代償として、**設定を間違えても警告が出ない**。だから統計ファイルで
「受信0件」を検出する仕組みを入れている。

### 終端抵抗

CANバスは両端に120Ωの抵抗を付けるのが決まり。信号の反射を防ぐため。
**既に終端されているバスに3個目を足すと波形が崩れる**ので、この治具には実装しない。

## 3. 全体アーキテクチャ

### ハードウェアの流れ

```
測定対象 CAN1(500k) ─ TVS ─ 絶縁トランシーバ ─ ESP32内蔵TWAI ┐
                                                          ├→ ESP32 ─ SDカード
測定対象 CAN2(250k) ─ TVS ─ 絶縁トランシーバ ─ MCP2515(SPI) ─┘
```

**なぜCH2だけ外付けICなのか。** ESP32(classic)の内蔵CANコントローラ（TWAI）は
**1チャネルしかない**。2バス同時記録には外付けが必須で、MCP2515を追加した。

負荷の高い500kbpsを内蔵TWAI、250kbpsをMCP2515に割り当てている。
MCP2515は受信バッファが2段しかなく、高速なバスでは取りこぼしやすいため。

### ソフトウェアの流れ

```
[CAN CH1] → rxTaskTwai ─┐
                        ├→ リングバッファ ─→ writerTask ─→ SDカード
[CAN CH2] → rxTaskMcp  ─┘   (RAM上)          (別コア)
```

**3つの独立した処理**が並行して動く。これが設計の中核。

| タスク | 動作コア | 優先度 | 仕事 |
|---|---|---|---|
| `rxTaskTwai` | Core 1 | 20 | CH1の受信と打刻だけ |
| `rxTaskMcp` | Core 1 | 19 | CH2の受信と打刻だけ |
| `writerTask` | Core 0 | 5 | ファイル形式への変換とSD書き込み |
| `loop()` | Core 1 | 1 | ボタン、LED、シリアルコマンド |

### なぜ受信と書き込みを分けるのか

**SDカードは、書き込みが突然数百ミリ秒止まることがある。**
内部でウェアレベリング（書き込み位置の平準化）やガベージコレクションが走るため。

もし「受信したら即SDへ書く」という作りにすると、その数百ミリ秒の間に届いた
フレームが全部失われる。CH1が最大4,000フレーム/秒なので、300ms止まれば1,200件の欠落。

そこで、

1. 受信タスクは**RAM上のリングバッファに置くだけ**（数マイクロ秒で終わる）
2. 書き込みタスクが**別のコアで**バッファから取り出してSDへ書く

という分業にしている。SDが止まっている間もバッファに溜まり続けるので、
**バッファが溢れない限り1件も落ちない**。

実測では、リングバッファ1024段のうち最大12段しか使っていない（余裕率85倍）。

## 4. ESP32の2つのCPUコアとタスク

### マルチタスクとは

普通のArduinoプログラムは `setup()` と `loop()` しかなく、処理は1つずつ順番に実行される。
これだと「SDに書いている間はCANを受信できない」という問題が起きる。

ESP32は**FreeRTOS**というリアルタイムOSが動いていて、
**複数の処理を並行して走らせられる**。この単位を**タスク**と呼ぶ。

### タスクの作り方

```cpp
xTaskCreatePinnedToCore(
    rxTaskTwai,        // 実行する関数
    "rxTwai",          // 名前（デバッグ用）
    4096,              // スタックサイズ（バイト）
    nullptr,           // 引数
    20,                // 優先度（大きいほど優先）
    nullptr,           // タスクハンドル
    1                  // 動かすCPUコア番号
);
```

### 優先度とコアの割り当ての意味

ESP32には**Core 0** と **Core 1** の2つのCPUがある。

```
Core 1（受信担当）              Core 0（書き込み担当）
├ rxTaskTwai  優先度20          └ writerTask  優先度5
├ rxTaskMcp   優先度19
└ loop()      優先度1
```

**受信と書き込みを別コアに分けている**ので、SD書き込みが重くても受信は止まらない。

同じコア内では**優先度が高いタスクが優先される**。CH1（500kbps、より高速）を
CH2より高い優先度にしているのは、取りこぼしにくくするため。

### 「必ず眠る」ことの重要性

優先度の高いタスクがCPUを離さないと、**低い優先度のタスクが一切動けなくなる**。
これを**飢餓（starvation）**と呼ぶ。

タスクは以下のいずれかで「眠って」CPUを他に譲る必要がある。

| 関数 | 意味 |
|---|---|
| `vTaskDelay(n)` | n ティック（1ティック=1ms）眠る |
| `twai_receive(&msg, timeout)` | フレームが来るか、タイムアウトするまで眠る |
| `ulTaskNotifyTake(clear, timeout)` | 通知が来るか、タイムアウトするまで眠る |

**開発中、この「必ず眠る」を1箇所外してしまい、装置全体が無反応になるバグを出した**
（§16参照）。ループの中に必ずブロックする呼び出しがあるかは、毎回確認すべき点。

## 5. リングバッファ

### 何のためにあるか

受信タスクと書き込みタスクの間でデータを受け渡す**待ち行列**。
「受信の速さ」と「書き込みの速さ」の差を吸収する。

### 仕組み

固定長の配列を輪っかのように使う。

```
配列: [ ][ ][A][B][C][ ][ ][ ]
             ↑        ↑
            tail     head
          (読む位置)  (書く位置)
```

- **head**（書き込み位置）を進める＝データを入れる
- **tail**（読み出し位置）を進める＝データを取り出す
- 末尾まで行ったら先頭に戻る（＝リング）
- `head == tail` なら空、`head+1 == tail` なら満杯

配列サイズを2のべき乗にしておくと、位置の更新が
`(h + 1) & (N - 1)` という高速な演算だけで済む（割り算が不要）。

### SPSC（単一生産者・単一消費者）

このリングバッファには重要な制約がある。

- **head を書き換えるのは生産者（受信タスク）だけ**
- **tail を書き換えるのは消費者（書き込みタスク）だけ**

この約束を守ると、**ロック（排他制御）が不要**になる。
お互いが別の変数しか触らないので、衝突しようがないため。

ロックを使うと、ロック待ちで受信タスクが止まる可能性が出る。それを避けている。

だからCH1とCH2で**別々のリングバッファ**を持っている（生産者が1つずつになるように）。

### メモリバリア

ESP32は2つのコアがあるため、片方のコアで書いた内容がもう片方から
**すぐには見えない**ことがある（CPUが最適化のために書き込み順序を入れ替える）。

```cpp
buf_[h] = rec;          // ①データを書く
__sync_synchronize();   // ②メモリバリア
head_ = next;           // ③headを進める
```

もし①と③の順序が逆になると、消費者が「データが入った」と判断したのに
中身がまだ古い、という事故が起きる。`__sync_synchronize()` は
**「ここより前の書き込みを、ここより後の書き込みより先に完了させろ」**という指示。

### 満杯になったら

```cpp
if (next == tail_) {
    dropped_++;      // 捨てた数を数える
    return false;
}
```

**古いデータを上書きせず、新しいデータを捨てる。** そして捨てた件数を数えておき、
統計ファイルに出す。これで「ログが信用できるか」が後から判定できる。

### サイズの決め方

| リング | 段数 | サイズ | 何秒分か |
|---|---|---|---|
| CH1 | 2048段 | 約49 KB | 4,000 frame/s で約0.5秒 |
| CH2 | 1024段 | 約25 KB | 2,250 frame/s で約0.45秒 |

安価なSDカードの一時停止（数百ms）を吸収できる長さにしている。

v2.7から、このリングは**静的確保ではなくヒープ確保**になっている。
Wi-Fi/LTEの通信スタックが静的領域を圧迫してビルドが通らなくなったためで、
経緯は §15 の「リングバッファをヒープへ移した話」を参照。

記録終了時に `ring max used` を統計ファイルへ残すので、実機で余裕を確認したうえで
`config.h` の `RING_SIZE_CH1` / `RING_SIZE_CH2` を調整できる
（`#ifndef` ガードがあるので `build_flags` からも上書きできる）。

## 6. レコード形式とファイル形式

### 24バイト固定長レコード

1フレームを24バイトで表現する。

```cpp
struct CanRec {
  uint64_t ts_us;    // +0  受信時刻(µs)   8バイト
  uint32_t id;       // +8  CAN ID         4バイト
  uint8_t  dlc;      // +12 データ長       1バイト
  uint8_t  flags;    // +13 拡張ID/RTR     1バイト
  uint8_t  channel;  // +14 1 or 2         1バイト
  uint8_t  reserved; // +15 予備           1バイト
  uint8_t  data[8];  // +16 データ         8バイト
};                   //     合計          24バイト
```

**固定長にする理由**は、n番目のレコードが「32 + 24×n」バイト目にあると
計算だけで分かるから。可変長だと先頭から順に読む必要がある。

`static_assert(sizeof(CanRec) == 24)` を書いてあるのは、コンパイラが
勝手に隙間（パディング）を入れていないかをビルド時に検査するため。
ここがずれるとPC側の変換ツールが全く読めなくなる。

### なぜテキストではなくバイナリなのか

当初はASCテキスト形式で保存する予定だった。比較するとこうなる。

| 形式 | 1フレーム | 6,250 frame/s | 10分 |
|---|---|---|---|
| ASCテキスト | 約64バイト | 約400 kB/s | 約240 MB |
| **バイナリ** | **24バイト** | **約150 kB/s** | **約90 MB** |

標準の `SD` ライブラリの実効速度は300 kB/s〜1 MB/s程度なので、
**ASCだと安価なカードでは間に合わない**。

加えて、テキスト化には数値を文字列に変換する処理（`snprintf`）が必要で、
これが1件あたり数十マイクロ秒かかる。6,250件/秒だとCPU時間の無視できない割合を食う。

**「PC側でどうせ変換するのだから、MCUは生データを吐くだけにする」**という判断。

### ファイル全体の構造

```
┌──────────────────────────┐
│ ヘッダ 32バイト            │  magic, version, ビットレート, 開始時刻
├──────────────────────────┤
│ レコード 24バイト × N      │  フレームの本体
└──────────────────────────┘
```

ヘッダに `"CANLOG02"` という**マジックナンバー**を入れてある。
PC側は最初にこれを確認して、正しいファイルかを判定する。

## 7. タイムスタンプ

### 2種類の「時刻」

この治具は**性質の違う2つの時刻**を扱う。混同しやすいので分けて理解する。

| | 相対時刻 | 絶対時刻 |
|---|---|---|
| 何を表すか | 記録開始からの経過時間 | 実世界の何時何分 |
| 供給源 | `esp_timer_get_time()` | RTC（MCP7940N） |
| 分解能 | **1マイクロ秒** | 1秒 |
| 用途 | **フレーム間隔の解析、再生** | 他の記録との突合 |
| 無いとどうなるか | 解析不能 | 「いつのログか」が不明になるだけ |

### 相対時刻：esp_timer_get_time()

ESP32起動からの経過マイクロ秒を返す。64bitなので約58万年オーバーフローしない。

```cpp
rec.ts_us = esp_timer_get_time();   // 受信した瞬間に打刻
```

**この打刻を受信タスクの先頭で行う**のが重要。
SDに書くときに打刻すると、書き込み待ちの時間が誤差として乗ってしまう。

### 精度の限界（正直な話）

ESP32のTWAIもMCP2515も**ハードウェアで受信時刻を記録する機能がない**。
だから「ソフトがフレームを取り出した時刻」で代用している。

| | この治具 | PC接続型インタフェース |
|---|---|---|
| 打刻方法 | ソフトウェア | ハードウェア |
| 通常時の誤差 | ±数十µs〜±100µs | ns〜µs |
| バースト時 | 数ms遅れることがある | 影響なし |
| フレームの順序 | 保証される | 保証される |

つまりこの治具は**「何が起きたか」の解析には十分だが、「何マイクロ秒後に起きたか」の
精密測定には向かない**。バス負荷率の測定やエラーフレームの解析が必要なら
従来どおりPC接続型インタフェースを使う、という線引きにしている。

### 絶対時刻：RTCとUTC

RTCには**現地時刻（日本時間）**を設定する。現地作業者が見て分かるようにするため。
ファームウェアが内部でUTCに変換して `unix_time` に格納する。

```
RTCの値（JST）  ─ 9時間 →  unix_time（UTC）  ─ PC側で+9時間 →  表示（JST）
```

**なぜわざわざUTCで保存するのか。** 世界中どこで記録しても一意に定まる基準だから。
タイムゾーンをまたぐと現地時刻は曖昧になる。

## 8. 2チャネルのマージ

### 問題

CH1とCH2で別々のリングバッファを持っているので、
そのまま書き出すとファイル内で時刻がバラバラになる。

### マージの考え方

両方のバッファの**先頭を覗いて、時刻が古い方を取り出す**。

```cpp
if (両方にデータがある) {
    return (t1 <= t2) ? CH1から取り出す : CH2から取り出す;
}
```

### 片方が空のときの難しさ

CH1にだけデータがあるとき、すぐ書き出してよいだろうか。
**まだCH2に、もっと古いフレームが後から積まれるかもしれない。**

そこで**5ミリ秒の猶予**を設けている。

```cpp
if (now - t1 < MERGE_LAG_US) return false;   // まだ待つ
```

「5ms前より古いフレームなら、もう他方に追い抜かれる心配はない」という判断。

### それでも完璧ではない

この方式は「ほぼ順番どおり」にはなるが、保証はしない。
そこで**PC側の変換ツールで必ず時刻ソートする**という二段構えにしている。

```python
records.sort(key=lambda r: r[0])   # 保険
```

MCUで完璧を目指すより、**PC側で確実に直す方が安全で簡単**という判断。
59,010件のソートはPCなら一瞬で終わる。

## 9. 状態機械

### 5つの状態

```
        [電源ON]
           ↓
      ┌─ ST_IDLE ─────┐  LED消灯
      │      ↓開始ボタン │
      │  ST_LOGGING    │  LED点滅
      │      ↓停止ボタン │
      │  ST_DRAINING   │  LED点滅（残りを書き出し中）
      │      ↓         │
      │  ST_STOPPED ───┘  LED点灯
      │
      └─ ST_ERROR         LED高速点滅
```

| 状態 | 意味 |
|---|---|
| `ST_IDLE` | 待機中。開始ボタン待ち |
| `ST_LOGGING` | 記録中 |
| `ST_DRAINING` | 停止処理中。受信は止めたが、バッファに残ったデータを書き出している |
| `ST_STOPPED` | 完全に停止。**SDカードを抜いてよい** |
| `ST_ERROR` | 異常 |

**アップロード機能を足しても状態は増やしていない。**
「記録していないとき」の裏で動く処理として実装し、状態機械そのものは触っていない。

既存の縮退保存や異常復帰のロジックは、この状態機械を前提に組んである。
状態を1つ増やすと、遷移表の全マス目を見直すことになる。
機能を足すときは、**まず「既存の状態の内側で表現できないか」を考えたほうが安全**。

### ST_DRAINING がある理由

停止ボタンを押した瞬間、リングバッファにはまだ数百件のフレームが残っている。
すぐにファイルを閉じると、それが失われる。

そこで「受信は止めるが書き出しは続ける」という中間状態を置いている。

### 停止処理の順序

順序を間違えると資源が漏れたりクラッシュしたりする。

```
1. ST_DRAINING にする         ← 受信タスクが積むのをやめる
2. 50ms待つ                   ← 受信タスクが受信待ちから抜けるのを待つ
3. CANドライバを停止・解放     ← ここより前に抜けていないとクラッシュする
4. リングが空になるまで待つ
5. 書き込みバッファを吐き出す
6. ファイルを閉じる
7. 統計ファイルを書く
8. ST_STOPPED にする（LED点灯） ← 全部終わってから点灯させる
```

**8を最後にしている**のが肝。LED点灯＝「SDを抜いてよい」の合図なので、
ファイルを閉じる前に点灯させてはいけない。

### 縮退保存（異常時もログを残す）

記録中にSDの書き込みが失敗したとき、単にエラー状態にすると
**それまでのログも統計も残らない**。現地で「何が起きたか」が全く分からなくなる。

そこで、異常時も**正常停止と同じ手順を通す**設計にした。

```cpp
finalizeLogging(true);   // 引数は「異常終了かどうか」だけ
```

異常でも、そこまでのデータを書き出し、ファイルを閉じ、統計ファイルに
`exit: ABNORMAL` と `fault: SD write failed` を残してから高速点滅に入る。

### なぜエラー処理を loop() に集約するか

異常を検出するのは書き込みタスクや監視処理だが、
**後始末は必ず `loop()` から行う**というルールにしている。

理由は、書き込みタスクの中から「書き込みタスクの完了を待つ」処理を
呼ぶことができないから（自分自身を待つことになり固まる）。

```cpp
// 異常を検出した側は、要因を記録するだけ
g_fault = FAULT_SD_WRITE;

// loop() が拾って後始末する
if (g_state == ST_LOGGING && g_fault != FAULT_NONE) {
    finalizeLogging(true);
}
```

## 10. 割込みとISR

### 割込みとは

「何かが起きたら、今やっている処理を中断して、専用の関数を実行する」仕組み。
ポーリング（定期的に確認しに行く）より応答が速く、CPUも無駄にしない。

MCP2515は、フレームを受信すると `/INT` ピンをLowにする。
これをESP32が検出して、受信タスクを起こす。

### ISR（割込みハンドラ）の書き方

```cpp
static void IRAM_ATTR mcpIsr() {
  BaseType_t higherPriorityTaskWoken = pdFALSE;
  vTaskNotifyGiveFromISR(g_mcpTaskHandle, &higherPriorityTaskWoken);
  if (higherPriorityTaskWoken == pdTRUE) portYIELD_FROM_ISR();
}
```

**ISRには厳しい制約がある。**

| ルール | 理由 |
|---|---|
| `IRAM_ATTR` を付ける | 割込み中はフラッシュメモリを読めないことがある。RAM上に置く指定 |
| **可能な限り短くする** | ISR実行中は他の処理が全部止まる |
| `Serial.print` や `delay` を使わない | 長すぎる、内部でロックを取るため |
| SPI通信をしない | 同上。**通知だけしてタスクにやらせる** |

だからこのISRは「タスクを起こす」だけで、SPIでの読み出しは
`rxTaskMcp` に任せている。

### portYIELD_FROM_ISR() の意味（重要）

これを忘れると**性能が桁違いに落ちる**。実際に踏んだ。

`vTaskNotifyGiveFromISR()` は「このタスクを起こす」とFreeRTOSに伝えるだけ。
**すぐにそのタスクへ切り替わるとは限らない。**

```
portYIELD_FROM_ISR() なし:
  割込み発生 → ISR → 元の処理に戻る → …… → 次のティック(最大1ms後) → やっとタスクが動く

portYIELD_FROM_ISR() あり:
  割込み発生 → ISR → すぐにタスクへ切り替わる（数十µs）
```

250kbpsでは約444µsごとにフレームが来る。MCP2515の受信バッファは2段しかないので、
**1ms待つとちょうど埋まって3件目から溢れる**。

これが実際に起きて、周期メッセージの1.21%を取りこぼしていた（§16）。

### レベル割込みとエッジ割込み

MCP2515の `/INT` は**レベル出力**（未読フレームがある間ずっとLow）。
一方ESP32側は**立ち下がりエッジ**（HighからLowに変わった瞬間）で検出している。

ここに穴がある。

```
フレームA到着 → INT Low → エッジ検出 → タスク起床
タスクがAを読む間にフレームB到着 → INTはLowのまま（エッジが発生しない！）
タスクが「もう無い」と判断して眠る → Bが読まれないまま残る
```

対策として、**眠る前にピンの状態を直接確認**している。

```cpp
if (digitalRead(MCP_INT_GPIO) == HIGH) {   // Highなら未読なし
    ulTaskNotifyTake(pdTRUE, pdMS_TO_TICKS(5));   // 通知を待つ
}
// Lowならそのまま読みに行く
```

さらに保険として5msのタイムアウトも入れてある。

## 11. MCP2515ドライバ

外部ライブラリを使わず自作している（`src/mcp2515.h`）。
Listen-Only設定やビットタイミングを完全に制御したかったため。

### SPI通信の基本

MCP2515とは**SPI**という4本線のインタフェースで話す。

| 線 | 向き | 役割 |
|---|---|---|
| SCK | ESP32→MCP | クロック |
| SI (MOSI) | ESP32→MCP | データ送信 |
| SO (MISO) | MCP→ESP32 | データ受信 |
| /CS | ESP32→MCP | この石と話す間だけLowにする |

```cpp
spi_->beginTransaction(SPISettings(spiHz_, MSBFIRST, SPI_MODE0));
digitalWrite(cs_, LOW);     // 通信開始
spi_->transfer(CMD_READ);   // コマンド送信
spi_->transfer(addr);       // アドレス送信
v = spi_->transfer(0x00);   // 読み出し（ダミーを送ると返ってくる）
digitalWrite(cs_, HIGH);    // 通信終了
spi_->endTransaction();
```

SPIは**送信と受信が同時に起きる**。読むときも何か送る必要があるので `0x00` を送っている。

### SDカードと別のSPIバスにしている理由

ESP32にはSPIコントローラが2つある（VSPIとHSPI）。

- **SDカード → VSPI**
- **MCP2515 → HSPI**

同じバスを共有すると、SDの書き込み中はMCP2515を読めない。
SDは数百ms止まることがあるので、その間にCH2が溢れる。**物理的に分けるのが確実。**

### 初期化の手順

```cpp
1. ハードウェアリセット（/RESETピンをLow→High）
2. ソフトウェアリセット（SPI命令 0xC0）
3. コンフィグモードになっているか確認
4. ビットタイミング設定（CNF1/CNF2/CNF3）
5. 全フレーム受信に設定（フィルタ無効）+ ロールオーバ有効
6. 受信割込みを有効化
7. Listen-Onlyモードへ移行
8. 本当にListen-Onlyになったか確認
```

**設定した後に必ず読み返して確認している**のがポイント。
SPIの配線不良やはんだ不良は、書き込みだけでは検出できない。

### ビットタイミング（サンプルポイント）

CANは1ビットの中の**どこで電圧を読むか**を設定できる。これをサンプルポイントと呼ぶ。

```
1ビットの時間を16分割（TQ = Time Quantum）

|Sync|  PropSeg  | PhaseSeg1 |PS2|
| 1  |     6     |     7     | 2 |
                              ↑
                         ここで読む = 14/16 = 87.5%
```

**遅めに読むほうがノイズに強い。** 信号の立ち上がりが落ち着いてから読めるため。
CiA（CAN in Automation）は87.5%を推奨している。

ネット上によくあるMCP2515のサンプルコードは、この値が**56.25%**になっている
定数表を使っていることが多い。動作はするが、バスの立ち上がりリンギングに弱い。
本ドライバでは3レート共通で87.5%になるよう独自に算出している。

| ビットレート | CNF1 | CNF2 | CNF3 |
|---|---|---|---|
| 500 kbps | 0x00 | 0xB5 | 0x81 |
| 250 kbps | 0x01 | 0xB5 | 0x81 |
| 125 kbps | 0x03 | 0xB5 | 0x81 |

### 受信バッファとロールオーバ

MCP2515には受信バッファが**RXB0とRXB1の2つだけ**しかない。

`BUKT` ビットを立てると、RXB0が埋まったとき自動的にRXB1へ回してくれる
（ロールオーバ）。これで実質2段のバッファとして使える。

3件目が来る前に読み出せないと**溢れて失われる**。
だから割込みの応答速度が決定的に重要だった（§10）。

### IDの組み立て

MCP2515は受信したIDを4つのレジスタに分けて持っている。
これを元の数値に組み立て直す必要がある。

```cpp
if (拡張ID) {
  id = (b[0] << 21)              // SIDH: ID[28:21]
     | ((b[1] >> 5) << 18)       // SIDL上位3bit: ID[20:18]
     | ((b[1] & 0x03) << 16)     // SIDL下位2bit: ID[17:16]
     | (b[2] << 8)               // EID8: ID[15:8]
     | b[3];                     // EID0: ID[7:0]
} else {
  id = (b[0] << 3) | (b[1] >> 5);  // 標準IDは11bit
}
```

このビット割りはデータシートで定義されている。1箇所間違えるとIDが化ける。

## 12. RTCドライバ

`src/mcp7940.h`。I2C通信で時刻を読み書きする。

### I2Cの基本

SPIより線が少ない（2本）。**SDA**（データ）と**SCL**（クロック）だけ。
複数のICを同じ2本にぶら下げられ、**アドレス**で区別する。

MCP7940Nのアドレスは `0x6F`。

両方の線を抵抗（4.7kΩ）で電源に引き上げておく必要がある（プルアップ）。
ICは線を「Lowに引っ張る」ことしかできない仕組みのため。

### BCD形式

RTCは時刻を**BCD（Binary Coded Decimal）**で持っている。
これは「10進数の各桁を4ビットずつで表す」形式。

```
10進の 45  →  BCDでは 0x45（上位4bit=4, 下位4bit=5）
```

人間が読みやすい代わりに、計算には使えないので変換が必要。

```cpp
static uint8_t bcd2bin(uint8_t v) { return (v >> 4) * 10 + (v & 0x0F); }
static uint8_t bin2bcd(uint8_t v) { return ((v / 10) << 4) | (v % 10); }
```

### MCP7940Nで忘れると動かない3つのこと

| 項目 | レジスタ | 内容 |
|---|---|---|
| **発振器の起動** | RTCSEC bit7 = ST | **1を書かないと時計が動かない**（工場出荷時は0） |
| **バックアップ有効化** | RTCWKDAY bit3 = VBATEN | **デフォルト無効**。忘れると電源断で時刻が消える |
| 発振の確認 | RTCWKDAY bit5 = OSCRUN | 実際に回っているかの確認 |

**「電源を入れれば時計が動く」わけではない**のがポイント。
起動時に `oscillator stopped` と出るのは、`SETTIME` していなければ正常な状態。

### 32.768kHz水晶の起動は遅い

音叉型の32.768kHz水晶は**発振開始まで数百ms〜数秒**かかる。
16MHzの水晶が数msで起動するのとは桁が違う。

開発中、発振待ちを200msで打ち切る実装にしていたため
「水晶が壊れている」と誤判定していた。5秒に延ばして解決した（§16）。

### 日付の計算

「1970年1月1日から何秒経ったか」（UNIX時刻）への変換に、
**Howard Hinnantのdays_from_civilアルゴリズム**を使っている。

うるう年の判定（4で割れる年はうるう年、ただし100で割れる年は除く、
ただし400で割れる年はうるう年）を含めて、分岐なしで計算できる有名な実装。

標準ライブラリの `mktime()` を使わないのは、タイムゾーン設定に依存せず
確実に動かすため。実装は標準ライブラリと照合して検証済み（2099年まで、うるう年含む）。

### デジタルトリミング

水晶の誤差をソフトで補正できる。

| 項目 | 値 |
|---|---|
| 補正範囲 | ±129 ppm |
| 分解能 | 1.017 ppm / step |
| 動作 | 1分ごとにクロックパルスを加減算 |

ppm（parts per million）は100万分の1。30 ppmずれていると
1日あたり `30 ÷ 1,000,000 × 86,400秒 = 2.6秒` ずれる計算。

## 13. SDカードへの書き込み

### まとめて書く

1フレームごとに書くのではなく、**4KB溜めてから一気に書く**。

```cpp
while (g_wlen < WRITE_CHUNK_BYTES && popMerged(rec, draining)) {
    memcpy(&g_wbuf[g_wlen], &rec, sizeof(CanRec));
    g_wlen += sizeof(CanRec);
}
if (g_wlen >= WRITE_CHUNK_BYTES) flushWriteBuffer();
```

SDカードは内部的に512バイト単位（セクタ）で管理されているので、
細かく書くと**同じセクタを何度も読み書きする**ことになり極端に遅くなる。

### flush（フラッシュ）の意味

`write()` しただけでは、データはまだメモリ上のバッファにいることがある。
`flush()` を呼ぶと確実にカードへ書き込まれ、ファイルシステムの管理情報も更新される。

2秒ごとにflushしている。**記録中に電源が切れても、直前2秒分しか失われない。**

毎回flushすると遅くなり、全くしないと電源断で全部失う。その折衷。

### ファイル名の採番

```cpp
for (uint16_t i = 1; i <= 9999; i++) {
    snprintf(g_logPath, ..., "/LOG%04u.BIN", i);
    snprintf(g_txtPath, ..., "/LOG%04u.TXT", i);
    if (!SD.exists(g_logPath) && !SD.exists(g_txtPath)) return true;
}
```

`.BIN` と `.TXT` の**両方**を確認している。
片方だけ残っているケース（前回の記録を途中で消したなど）で上書きしないため。

SDカードのルートには `CONFIG.TXT`（設定）と `UPLOADED.TXT`（アップロード進捗）も置かれるが、
採番は `LOG%04u` 形式しか見ないので**衝突しない**。

### 統計ファイル

ログ本体とは別に `LOG0001.TXT` を出す。これが**ログの信頼性の証明書**になる。

```
exit            : normal (stop button)
frames logged   : 2747
ring dropped    : 0
ctrl missed     : 0
result          : OK
```

現地の作業者はCANの中身は分からなくても、
**このファイルを見れば「ちゃんと録れたか」が判断できる**。

## 14. PC側の変換ツール

`tools/bin_to_blf.py`。Pythonで書かれた変換スクリプト。

### やっていること

```python
1. ヘッダ32バイトを読んで magic を確認
2. 24バイトずつレコードを読む
3. 時刻順にソート（2chマージの保険）
4. python-can の BLFWriter でBLFへ書き出す
```

### 構造体の読み方

C言語の構造体と同じレイアウトで読む必要がある。

```python
REC = struct.Struct("<QIBBBB8s")
#                    │└─ 8s: data[8]
#                    │  BBBB: dlc, flags, channel, reserved
#                    │ I: id (uint32)
#                    └ Q: ts_us (uint64)
#                   < = リトルエンディアン（下位バイトが先）
```

**`<`（リトルエンディアン）の指定を忘れると全部化ける。**
ESP32もPCも通常リトルエンディアンだが、明示しておくのが安全。

### タイムゾーンの落とし穴

治具はUTCで保存する。python-canはBLFヘッダに**UTCをそのまま書く**。
ところが**CANalyzerはそのフィールドを現地時刻として表示する**。

つまり何もしないと**9時間ずれる**。

対策として、全タイムスタンプに現地のUTCオフセットを加算している。

```python
msg.timestamp = start_epoch + rel + tz_shift
```

**全フレームを同じ量だけずらすので、フレーム間の相対時刻は変わらない。**
BLF内の各フレームは「開始時刻からの差分」で記録されるため。

## 15. ログの自動アップロード

v2.6から、記録したログをWi-Fi経由でサーバーへ自動送信する機能が入った。
ここでは「なぜこう作ったか」を中心に説明する。

将来的にはWi-FiをLTE（SIM7600）へ置き換えて、現地へ行かずにログを回収できるようにする計画で、
**通信方式に依存しない部分を先に作って検証する**のがこの実装の目的でもある。

### 何のために要るか

治具を設置したあと、現地へ行かないと次のことが分からない。

- ちゃんと録れているのか
- 録れたログは信用できるのか（取りこぼしは無いか）
- SDカードの残りはあるか

**「行ってみたら録れていなかった」を無くす**のが第一の目的で、ログ本体の回収は二番目。
そのため統計ファイル（`LOGxxxx.TXT`、数KB）を**ログ本体より先に**送る作りにしている。

### 大原則：記録中は絶対に動かさない

この治具は「取りこぼしゼロ」を売りにしている。
アップロードがCPUやSDカードを奪えば、その前提が崩れる。

そこで、動いてよい状態を1か所で判定する。

```cpp
static bool upCanRun() {
  if (g_state == ST_LOGGING || g_state == ST_DRAINING) return false;
  if (g_fault == FAULT_SD_INIT || g_fault == FAULT_SD_WRITE) return false;
  return true;
}
```

記録中と停止処理中は問答無用で止まる。SDが壊れているときも触らない。
逆に `ST_ERROR` でも（SD以外の異常なら）動かすのは、**そこまでのログを回収したいから**。

### 中断のハンドシェイク（順序が命）

開始ボタンが押されたとき、アップロード側はSDのファイルハンドルを握っている可能性がある。
`startLogging()` は次の順番で手放させてから記録を始める。

```cpp
uploaderRequestStop();      // 1. 中断を要求する
uploaderWaitIdle(3000);     // 2. ファイルを閉じるまで待つ
uploaderWifiOff();          // 3. Wi-Fiを落とす
  ↓
hardCleanup();              // 4. ここで初めて SD.end() / SD.begin()
```

**この順序を逆にすると壊れる。** 先に `SD.end()` を呼ぶと、アップロード側が持っている
`File` オブジェクトが無効になり、次のアクセスで未定義動作になる。

中断の判定は送信ループの**1KBごと**に入れている。応答待ちで長く止まらないので、
実測では数十msで抜ける。

```cpp
while (remain > 0) {
  if (upShouldAbort()) { cli.stop(); return false; }   // ここ
  ...
  vTaskDelay(1);   // loop()を飢餓にしないため（§4参照）
}
```

### HTTP PUT で送る

送信は**HTTPのPUTメソッド**を使う。
「このURLに、このファイルを置け」という意味の、いちばん素直な方法。

```
PUT /canlog/JIG001/20260901_150227_LOG0006_001.bin HTTP/1.1
Host: 192.168.10.104:8080
Content-Type: application/octet-stream
Content-Length: 1048576
Connection: close

（ここから1,048,576バイトのデータ）
```

外部ライブラリを使わず `WiFiClient` で直接この文字列を組み立てている。
HTTPライブラリを入れるとメモリを食うし、中断制御が自分でできなくなるため。

`Content-Length` を先に宣言するので、**途中で切れたらサーバー側が気づける**。
これが後述の「壊れたファイルを残さない」仕組みになる。

### なぜ分割して送るのか

1MBずつに区切って送る。理由は3つ。

| 理由 | 内容 |
|---|---|
| 中断されても損失が小さい | 記録開始で中断されたとき、失うのは送りかけの1パートだけ |
| 回線が切れても再開できる | 圏外・瞬断の復帰後、失敗したパートから続けられる |
| サーバー側の上限 | SORACOM Harvest Files はセルラー経由で1ファイル100MiBまで |

パートは別々のファイルとして置かれ、PC側で `merge_parts.py` を使って連結する。

```
20260901_150227_LOG0006_001.bin   1,048,576 byte
20260901_150227_LOG0006_002.bin     319,696 byte
        ↓ 連結
20260901_150227_LOG0006.bin       1,368,272 byte
```

### 分割サイズは大きいほうがよい

実測すると、1パートあたり**約80msの固定費**（TCP接続とHTTPの往復）がかかっていた。

| チャンクサイズ | 実効速度 |
|---|---|
| 16 KB | 89〜94 kB/s |
| 1024 KB | 124〜166 kB/s |

16KBだと1パート約180msのうち、100msがデータ転送で**80msが待ち時間**になる。
LTEに置き換えるとATコマンドの往復が毎パート発生するので、この固定費はさらに大きくなる。
**既定の1024KBを維持すること。**

### 壊れたファイルを残さない

送信の途中で中断すると、サーバー側には「宣言したサイズより少ないデータ」が届く。

```
[23:48:41] SHORT  .../LOG0006_001.bin  7168/1048576 byte
```

サーバーはこれを検出してファイルを書かず、400を返す。
治具側は失敗として扱い、待機に戻ってから**同じパスへ送り直す**。

**同じパスに送れば上書きされる**ので、何度リトライしても結果は同じになる。
この性質を「冪等（べきとう）」といい、通信が不安定な環境では設計の要になる。

### 進捗をどう覚えるか

`/UPLOADED.TXT` に追記していくだけの単純なテキスト。

```
0006,P,000,1024        part 0（統計TXT）完了。末尾はチャンクサイズ[KB]
0006,P,001,1024        part 1 完了
0006,D,002,1368272     全パート完了（総パート数, 総バイト数）
```

起動時に `D` の行だけを読んで、完了済みのLOG番号を**ビットマップ**（1250バイト）に展開する。
9999ファイル分を1250バイトで持てるので、ファイル一覧を持つより圧倒的に軽い。

```cpp
static uint8_t g_upDone[(9999 / 8) + 1];   // 1250 byte

static inline bool upDoneGet(uint16_t idx) {
  return (g_upDone[idx >> 3] >> (idx & 7)) & 1;
}
```

`idx >> 3` がバイト位置、`idx & 7` がそのバイトの中のビット位置。
8で割った商と余りを求める計算を、ビット演算で書いたもの。

### チャンクサイズを一緒に記録する理由

**パート番号は、チャンクサイズを前提にした値**である。

part 1 が指すのは「先頭から1チャンク分」だが、その「1チャンク」が1024KBなのか16KBなのかで
実際のオフセットがまったく変わる。設定を変えたあとに古い進捗を信じると、

```
記録上の進捗 = part 1 完了  →  part 2 から再開
実際のオフセット = (2-1) × 16KB = 16KB
                   ↑ 本来はここまでに1024KB送っているはずだった
```

となり、**先頭の大部分を飛ばした欠けたファイルができる**。

そこで進捗行にチャンクサイズを書いておき、読むときに照合する。
一致しない記録は無視するので、設定を変えれば自動的に先頭から送り直しになる。

```
[UP] LOG0006 : progress reset (chunk size changed). resend from part 0
```

### Wi-Fiは必要なときだけONにする

待機中ずっとWi-Fiを繋いでおくと、消費電流が増えるうえ、
**記録開始時にOFFにする処理が余計に必要**になる。

そこで「送るものが見つかったら接続、無くなったら切断」という動きにしている。

```
待機 → SDを走査 → 未送信あり → Wi-Fi ON → 送信 → 全部終わった → Wi-Fi OFF
```

### リングバッファをヒープへ移した話

Wi-Fiを有効にしたら、**ビルドが通らなくなった**。

```
region `dram0_0_seg' overflowed by 2488 bytes
```

ESP32のDRAMは「静的データ（`.bss`）を置ける領域」に**固定の上限**があり、
ヒープはその外側のDRAMも使える、という構造になっている。

Wi-Fiスタックが約40KBの静的バッファを持ち込んだ結果、
リングバッファ（約74KB）を静的確保したままでは入りきらなくなった。

対策は、**大きいものをヒープへ移す**こと。

```cpp
// v2.6まで
static SpscRing<RING_SIZE_CH1> g_ring1;        // .bss に 49KB

// v2.7
static SpscRing<RING_SIZE_CH1>* g_ring1 = nullptr;
// setup() で
g_ring1 = new (std::nothrow) SpscRing<RING_SIZE_CH1>();
```

`std::nothrow` を付けているのは、確保に失敗したときに例外ではなく `nullptr` を返させるため。
失敗したらタスクを起動せず `ST_ERROR` に落とす。

**この変更で、リングサイズの制約は「静的領域に入るか」から「ヒープに余裕があるか」に変わった。**
実測で初期化後のヒープ残量は約164KBあり、まだ増やす余地がある。

### 設定ファイル（CONFIG.TXT）

SSIDや送信先をソースに直書きすると、変えるたびに再ビルドと
CH340E特有の手動書き込み操作（BOOT+EN）が必要になる。

そこでSDカードの `/CONFIG.TXT` から読むようにした。

```
WIFI_SSID   = your-ssid
WIFI_PASS   = your-password
UP_HOST     = 192.168.10.104
UP_CHUNK_KB = 1024
```

パーサは60行程度の自前実装で、**外部ライブラリを使わず、動的メモリも確保しない**。
不正な行は読み飛ばして既定値で動き、**起動は絶対に止めない**（既存の設計方針と同じ）。

### LTE化への備え

通信方式に依存するのは**3つの関数だけ**にしてある。

| 関数 | Wi-Fi版 | LTE版でやること |
|---|---|---|
| `upWifiUp()` | `WiFi.begin()` | ロードスイッチON、`AT` 応答待ち、`AT+CNMP=38`、`AT+CGACT` |
| `upWifiDown()` | `WiFi.mode(WIFI_OFF)` | `AT+CPOF` → 無応答確認 → ロードスイッチOFF |
| `upPutRange()` | `WiFiClient` で直接PUT | `AT+HTTPINIT` → `AT+HTTPDATA` → `AT+HTTPACTION=1` |

分割・再送・進捗管理・中断処理はそのまま使える。
**`upPutRange()` の引数と戻り値（remotePath, File&, offset, length → bool）を変えないこと**が、
差し替えを楽にするための約束になっている。

## 16. 開発中に踏んだバグと教訓

実際に発生した不具合と、その原因・対策。同種の設計をするときの参考に。

### バグ1: ISRでタスク切り替えを要求していなかった

| 項目 | 内容 |
|---|---|
| **症状** | CH2で周期メッセージの1.21%が欠落（ID 341は17.3%） |
| **原因** | `vTaskNotifyGiveFromISR()` の第2引数に `nullptr` を渡していた |
| **結果** | 受信タスクの起床が**次のティック（最大1ms）まで遅延** |
| **なぜ問題か** | 250kbpsではフレーム間隔が444µs。1ms待つと2段のバッファが埋まる |
| **対策** | `portYIELD_FROM_ISR()` を追加。起床遅延が1ms→数十µsに |

**どう気づいたか。** 実機ログを解析したところ、

- 1回の起床で読んだフレーム数が「1件…1,672回 / **2件…1,311回**」
- **起床間隔の最小値が999µs**（1000µs未満は3,026回中9回だけ）

という分布が出た。1msに量子化されているのはティック境界で起きている証拠だった。

**教訓**: 統計を残しておくと、後から定量的に原因を特定できる。
「なんとなく遅い」ではなく「1msに量子化されている」まで分かると原因が絞れる。

### バグ2: 修正した際に飢餓バグを作り込んだ

| 項目 | 内容 |
|---|---|
| **症状** | シリアルもボタンもLEDも全部無反応。起動ログも途中で止まる |
| **原因** | `/INT` のレベルチェックを追加した際、「記録中でない」判定を**その後ろ**に置いた |
| **結果** | CH2をバスに接続した待機状態で、**どこでもブロックせずに回り続けた** |
| **なぜ問題か** | 優先度19・コア1固定のため、優先度1の `loop()` が飢餓状態に |
| **対策** | 状態判定を先頭へ移動。記録中でなければ必ず `vTaskDelay()` |

**どう気づいたか。** 起動ログの最後の2行（`free heap after init` と
`type HELP for serial commands.`）**だけが出ていなかった**。
これは `setup()` が完走していない＝タスク生成の直後で止まっている、という意味だった。

**教訓**: 起動ログを段階的に出しておくと、どこで止まったかが一目で分かる。
また、**CH2を接続していない環境では絶対に再現しなかった**。
条件付きでしか出ないバグがあることを前提に、実環境に近い条件で試験する必要がある。

### バグ3: 異常時に復帰できなくなる

| 項目 | 内容 |
|---|---|
| **症状** | 一度エラーになると、開始ボタンを押しても復帰しない |
| **原因** | エラー時にCANドライバとファイルを解放していなかった |
| **結果** | 再開始しようとしても「既に初期化済み」で失敗し続ける |
| **対策** | `hardCleanup()` を追加し、記録開始の冒頭で必ず全解放 |

**教訓**: 「失敗したときに元の状態に戻す」処理は、正常系より書き忘れやすい。
**すべての失敗経路で資源が解放されるか**を意識的に確認する必要がある。

### バグ4: 水晶の起動待ちが短すぎた

| 項目 | 内容 |
|---|---|
| **症状** | `RTC write failed` が出て時刻設定できない |
| **原因** | 発振の立ち上がりを200msしか待っていなかった |
| **実際** | 32.768kHz水晶の起動には数百ms〜数秒かかる |
| **対策** | 5秒に延長。さらに「書き込みの成否」と「発振待ち」を分離 |

**教訓**: エラーメッセージが原因を誤って示すと、切り分けが大きく遠回りになる。
`RTC write failed`（I2Cの問題に見える）と表示していたため、
実際は発振待ちの問題なのに、はんだ不良を疑ってしまった。

**1つの戻り値に複数の意味を持たせない**。

### バグ5: コールド起動時にSD初期化が失敗する

| 項目 | 内容 |
|---|---|
| **症状** | 電源投入時は必ずLEDが高速点滅。リセットすると直る |
| **原因** | ESP32は約300msで初期化に入るが、SDカードは規格上最大1秒応答しなくてよい |
| **対策** | 起動時に300ms待機 + SD初期化を5回リトライ |

**教訓**: 「リセットすれば直る」で済ませない。現地作業者にとっては故障に見える。

### バグ6: 「統計のみ」設定が手動コマンドにも効いてしまった

`UP_STATS_ONLY = 1` は「自動では統計ファイルだけ送る」という設定のつもりだったが、
判定を送信関数の中に置いたため、**`UPLOAD LOG0007` と明示的に指定してもBINが送られなかった**。

| | |
|---|---|
| **症状** | 統計のみモードで、手動コマンドを打ってもログ本体が回収できない |
| **原因** | `upSendOneFile()` が自動／手動を区別せずに設定フラグを見ていた |
| **対策** | `forced` 引数を追加し、明示指定時は設定を無視する |

**教訓**: 「既定の振る舞い」と「明示的な指示」は別物として扱う。
設定は前者にだけ効かせる。

### バグ7: チャンクサイズを変えると欠けたファイルができた

分割サイズを1024KBから16KBに変えて再送したところ、先頭部分が抜けたファイルができた。

| | |
|---|---|
| **症状** | 設定変更後の再送で、先頭のパートが飛ばされる |
| **原因** | 進捗記録が「part 1 完了」としか持っておらず、**その1パートが何バイトだったかを記録していなかった** |
| **対策** | 進捗行にチャンクサイズを書き、読むときに照合する。不一致なら進捗を無効化する |

**教訓**: 番号やインデックスを保存するときは、**それを解釈するための前提も一緒に保存する**。
「part 1」は単体では意味を持たない。

### バグ8: 中断された指示が黙って消えていた

`UPLOAD 6` を実行中に記録を開始し、記録終了後に再開するはずが、
**まったく別のファイル（新しく録れたログ）が送られていた**。

原因は2段階あった。

| 段階 | 内容 |
|---|---|
| 1 | 中断されたとき、指定要求を積み直していなかった |
| 2 | 積み直すようにしたら、今度は `finalizeLogging()` が出す「走査やり直し要求」が**同じ変数を上書き**していた |

```cpp
// 修正前：同じ変数に2種類の要求を入れていた
static volatile uint16_t g_upReq = 0;   // 0=なし / 1..9999=指定 / 0xFFFF=走査

uploaderRequestScan() { g_upReq = UP_REQ_SCAN; }   // ← 積み直した「6」を潰す
```

**記録が終わるたびに必ず走査要求が出る**ので、中断された指定要求は100%失われていた。

```cpp
// 修正後：別々に持ち、指定を優先する
static volatile uint16_t g_upReq     = 0;      // 指定ファイル
static volatile bool     g_upScanReq = false;  // 走査のやり直し
```

**教訓**: 意味の違うものを1つの変数に詰め込むと、片方が片方を壊す。
「値が0以外なら指定、特別な値なら別の意味」という設計は、後から必ず破綻する。

この不具合は、**遠隔からコマンドでログを取りに行く運用では致命的**だった。
「LOG0007を送れ」という指示が、記録が1回入っただけで消えてしまう。

### 設計判断として効いたこと

| 判断 | 効果 |
|---|---|
| 統計ファイルを出す | 実機ログから定量的に原因を特定できた |
| 起動ログを段階的に出す | どこで止まったかが一目で分かった |
| リングバッファに `max used` を記録 | 「バッファは余裕」と分かり、原因を別の場所に絞れた |
| PC側でも時刻ソート | MCU側のマージが不完全でも実害が出ない |
| `static_assert` でサイズ検査 | 構造体レイアウトのずれをビルド時に検出 |
| 通信層を3関数に閉じ込めた | Wi-Fiで全機能を検証してからLTEへ差し替えられる |
| 中断を「失敗」と区別した | `fail=` が回線品質の指標として使える |
